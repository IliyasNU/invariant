## 1. Что такое Invariant простыми словами

**Invariant — инструмент, который проверяет Python-код на соблюдение заранее заданных правил устройства проекта.**

Представьте большой магазин. Есть отдел продаж, склад и бухгалтерия. Если любой сотрудник начнёт напрямую менять документы любого другого отдела, быстро возникнет путаница. В программе похожая проблема: разные части начинают слишком тесно зависеть друг от друга, и небольшое изменение ломает неожиданные места.

Разработчики договариваются о границах: например, код расчёта платежей не должен напрямую обращаться к конкретной базе данных. Но договорённость в документе легко забыть. Invariant превращает часть таких договорённостей в автоматические проверки.

Вы задаёте правило:

> «Код из `app.domain` не должен импортировать `app.infrastructure`».

Invariant читает отправленный исходный текст и сообщает:

> «В файле `app/domain/payment.py`, строка 1, нарушено правило: найден импорт инфраструктуры».

Он не придумывает правила за вас, не оценивает «красоту» всей архитектуры и не исправляет код автоматически. Его задача уже и конкретнее: последовательно проверять формальные ограничения.

Название отсылает к **инварианту** — условию, которое должно оставаться истинным, даже когда система изменяется. В этом проекте таким условием может быть сохранение границ между слоями программы.

## 2. Короткое описание для работодателя

Invariant — портфолио-проект backend-инструмента для детерминированного статического анализа архитектурных правил Python-проектов. Одно автономное ядро используется командной строкой, HTTP API и интеграцией с GitHub pull requests.

Сервис хранит проекты, правила и историю анализов в PostgreSQL. GitHub-задачи обрабатываются отдельным worker-процессом через очередь в той же базе: с повторными попытками, временным владением задачей и защитой от повторной доставки webhook. Результаты содержат координаты нарушений, счётчики, исход проверки и снимок конфигурации. Есть JSON- и SARIF-экспорт, включая экспорт исторического запуска.

Проект показывает следующие инженерные навыки:

- проектирование API и валидацию входных данных;
- работу с SQLAlchemy, PostgreSQL и Alembic;
- разделение вычислительного ядра и серверных адаптеров;
- анализ AST и областей видимости Python;
- интеграцию с внешним HTTP API и обработку его отказов;
- фоновые задачи без отдельного брокера сообщений;
- автоматические тесты, упаковку Python-пакета и Docker Compose;
- профилирование с проверкой, что оптимизация не меняет результаты.

Это описание реализованных возможностей, а не заявление о промышленной эксплуатации. Из репозитория нельзя сделать вывод о количестве реальных пользователей, SLA или работе под большой производственной нагрузкой.

## 3. Какую проблему решает проект

Рассмотрим условное приложение платежей:

```text
src/
└── app/
    ├── domain/            расчёты и правила предметной области
    │   └── payment.py
    ├── infrastructure/    работа с БД и внешними сервисами
    │   └── db.py
    └── api/               приём HTTP-запросов
```

**Предметная область**, или domain, — смысловая часть приложения: например, как посчитать стоимость заказа. **Инфраструктура** — технические детали: какая используется база, какой HTTP-клиент отправляет запросы.

Если в `payment.py` появляется:

```python
from app.infrastructure.db import engine
```

код расчётов оказывается связан с конкретной технической реализацией. Возможно, команда разрешает такую зависимость. Но если команда решила её запретить, Invariant может проверять это решение при каждом изменении.

Важно: Invariant **не доказывает**, что ваша архитектура правильная. Он проверяет, соответствует ли код указанным ограничениям. Если правило выбрано плохо, инструмент добросовестно будет проверять плохое правило.

## 4. Что можно делать сейчас

В версии 1.2.0 доступны:

1. Проверка файлов локально через команду `invariant`.
2. Проверка файлов, изменённых между Git-коммитами.
3. Создание проектов и правил через API.
4. Импорт и экспорт конфигурации `invariant.toml`.
5. Анализ исходного текста, переданного HTTP-запросом.
6. Постановка GitHub pull request в очередь на анализ.
7. Приём подписанных webhook от GitHub.
8. Просмотр истории, отдельных нарушений и статистики.
9. Экспорт результатов в JSON и SARIF 2.1.0.
10. Необязательный комментарий с результатами в GitHub PR.

Два режима использования принципиально различаются:

| Режим | Что требуется | Где живёт результат |
| --- | --- | --- |
| CLI — командная строка | Python, установленный пакет, файлы и конфигурация | Терминал или сохранённый отчёт |
| Backend-сервис | API, PostgreSQL; worker для GitHub-задач | База данных и ответы API |

Для локальной CLI-проверки не нужны PostgreSQL, Docker, API-ключ, GitHub-токен или запущенный сервер.

Python 3.14+ требуется для запуска самого Invariant. Проверяемый проект может быть рассчитан и на более старую версию Python, если его исходный текст принимает используемый парсер. Проверка не является полной проверкой совместимости со всеми версиями языка.

`jsonschema` использовался как временный инструмент проверки SARIF. Это **не обязательная runtime-зависимость** Invariant.

Ядро и CLI в собранном wheel зависят от Pydantic. Серверные библиотеки вынесены в группу зависимостей `server`. Поэтому установка CLI не требует тащить за собой FastAPI и PostgreSQL-драйвер.

## 7. Архитектура: как части соединены

```text
Локальные файлы ──> CLI ──────────────────────────────┐
                                                    v
HTTP с текстом файлов ──> FastAPI ──> адаптер ──> одно ядро анализа
                                                    |
GitHub PR ──> API/webhook ──> PostgreSQL-очередь       |
                                  |                 |
                                  v                 |
                               worker ──> GitHub ───┘
                                  |
                                  v
                       сохранённый запуск и диагностики
                                  |
                                  v
                       история / статистика / JSON / SARIF
```

Главное решение: **сама проверка не привязана к способу получения файлов**. Ей не нужно знать, пришёл ли текст из терминала, HTTP-запроса или GitHub.

У проекта две основные области:

- `src/invariant/` — самостоятельное вычислительное ядро и CLI;
- `app/` — сервер: API, БД, очередь, GitHub, авторизация и эксплуатационная логика.

Это разделение можно объяснить так: «проверяющий механизм» отделён от «доставки документов и хранения результатов». Добавлять новый способ доставки проще, когда не приходится заново писать проверки.

API и worker — разные процессы, но это не система микросервисов. Они используют одну кодовую базу и общую PostgreSQL. Отдельных Redis, брокера очередей или Kubernetes здесь нет.

## 8. Как устроен анализ кода

Основная функция находится в `src/invariant/engine.py` и называется `analyze`.

Обработка выглядит так:

1. Получить тексты файлов, правила и настройки проекта.
2. Нормализовать пути и определить Python-имена модулей.
3. Учесть корни исходников и исключения.
4. Разобрать текст через `ast.parse`.
5. Применить подходящие включённые правила.
6. Собрать нарушения и ошибки анализа.
7. Посчитать итог, отсортировать диагностики и вернуть результат.

Пример: Python видит `import os` не как случайную строку текста, а как узел импорта. Поэтому комментарий `# import os` не становится настоящим импортом и не должен вызывать такое же нарушение.

### Почему проверяемый код не запускается

Invariant строит AST, но не выполняет полученную программу и не импортирует её как модуль. Если в проверяемом файле написано «удали файл», анализатор изучает конструкцию, а не исполняет это действие.

Это важное ограничение механизма, но не универсальная гарантия безопасности сервиса. Слишком большие или сложные входные данные всё равно могут расходовать ресурсы; для них предусмотрены лимиты и обработка ошибок.

### Что делают правила

`src/invariant/rules.py` содержит проверки. `src/invariant/calls.py` отдельно разбирает области видимости и имена вызовов: например, понимает, что после `import os as operating` вызов `operating.system(...)` относится к `os.system`.

При этом переменная с похожим именем не обязана быть импортированным модулем. Анализатор учитывает часть таких переопределений и не считает любое слово `system` системным вызовом.

Импорты учитываются и внутри функций, условных блоков и `if TYPE_CHECKING:`. Сервис не пытается предсказать, выполнится ли конкретная ветка во время работы программы.

### Что оптимизировали

Раньше каждое правило импортов заново обходило целое дерево файла. Теперь импортирующие узлы собираются один раз на файл. Список запрещённых префиксов подготавливается один раз на правило за анализ. После достижения лимита выдачи лишние нарушения считаются без создания их сообщений и объектов диагностики.

Для одинаковых входных данных, порядка файлов/правил, версии движка и настроек результат воспроизводим. При ограниченной выдаче от порядка обработки зависит, какие именно первые нарушения попали в сохранённый список; полные счётчики при этом сохраняются.

## 9. Правила и конфигурация: пример с объяснением

Файл `invariant.toml` — договорённости конкретного проверяемого проекта. Это **не** файл с паролем к БД.

```toml
version = 1

[project]
source_roots = ["src"]
exclude_paths = ["tests/", "**/migrations/*.py"]
fail_on = "error"

[[rules]]
key = "domain-isolation"
name = "Предметная область не зависит от инфраструктуры"
rule_type = "forbidden_import"
source_pattern = "app.domain.*"
forbidden_imports = ["app.infrastructure", "fastapi", "sqlalchemy"]

[[rules]]
key = "no-shell"
name = "Предметная область не запускает команды"
rule_type = "forbidden_call"
source_pattern = "app.domain.*"
forbidden_calls = ["os.system", "subprocess", "builtins.eval"]

[[rules]]
key = "absolute-imports"
rule_type = "no_relative_import"
source_pattern = "app.*"
severity = "warning"

[[rules]]
key = "small-files"
rule_type = "max_file_lines"
source_pattern = "app.domain.*"
max_lines = 400
```

Разберём поля:

- `version = 1` — версия **формата конфигурации**, а не версия программы 1.2.0.
- `source_roots` — каталоги, от которых строятся имена модулей. С корнем `src` файл `src/app/domain/payment.py` становится `app.domain.payment`.
- `exclude_paths` — пути, которые не надо проверять.
- `fail_on` — минимальный уровень нарушения, который проваливает проверку.
- `key` — устойчивый идентификатор правила. Он попадает в отчёты.
- `name` — понятная человеку подпись; необязательна.
- `enabled` — включено ли правило; по умолчанию `true`.
- `severity` — `error` или `warning`; по умолчанию `error`.
- `source_pattern` — к каким **именам модулей** применять правило.

Четыре вида правил:

| Тип | Пример | Что будет найдено |
| --- | --- | --- |
| `forbidden_import` | Запрет `app.infrastructure` в `app.domain.*` | `from app.infrastructure.db import engine`. Запрещены также подмодули, но не `app.infrastructure_extra`. |
| `forbidden_call` | Запрет `os.system` | `import os as operating`, затем `operating.system("echo hello")`. |
| `no_relative_import` | Предпочитать абсолютные импорты | `from .models import Payment` создаст диагностику. |
| `max_file_lines` | Не более 400 строк | Файл из 401 строки нарушит правило; место нарушения — строка 401. |

Не путайте шаблоны: `app.domain.*` относится к имени модуля, а `tests/**` — к пути. Для путей `*` не проходит через границу каталога, а `**` проходит. Запись `tests/` нормализуется в исключение всего дерева `tests/**`.

В конфигурации можно использовать `invariant.toml` либо секцию `[tool.invariant]` в `pyproject.toml`. Неизвестные поля и некоторые неоднозначные настройки отвергаются: например, пересекающиеся корни исходников.

## 10. Как читать результат и не перепутать успех с отсутствием проверки

У запуска есть два разных понятия.

**`status` — что произошло с выполнением задачи:**

| Статус | Значение |
| --- | --- |
| `queued` | Задача записана в очередь. Проверка ещё не выполнена. |
| `running` | Worker обрабатывает задачу. |
| `completed` | Проверка завершилась и сформировала результат. |
| `failed` | Запуск технически не смог завершиться, например из-за недоступного GitHub. |

**`outcome` — что нашла завершённая проверка:**

| Итог | Значение | `passed` |
| --- | --- | --- |
| `pass` | Применимые проверки выполнены, блокирующих нарушений нет | `true` |
| `fail` | Найдено хотя бы одно блокирующее нарушение | `false` |
| `incomplete` | Часть входа не удалось проверить, а блокирующего нарушения не найдено | `null` |
| `not_applicable` | Ни одна включённая проверка не применилась | `null` |

`completed` не означает `pass`. Например, проверка могла успешно завершить работу и обнаружить нарушения.

Если один файл нарушает правило, а другой синтаксически сломан, итог будет `fail`, но в диагностике также останется ошибка анализа второго файла. Поэтому смотрите не только на одно поле `outcome`, но и на `summary.analysis_errors`.

Сводка разделяет:

- `summary.errors` — нарушения правил уровня `error`;
- `summary.warnings` — нарушения уровня `warning`;
- `summary.analysis_errors` — препятствия самой проверке, например некорректный Python-синтаксис.

При `fail_on = "error"` одно предупреждение допускает `pass`. При `fail_on = "warning"` оно уже блокирует проверку.

API и worker сохраняют первые **1000 нарушений правил** на запуск, но продолжают считать все. Технические ошибки анализа не обрезаются этим лимитом. Поэтому `violation_count = 1005` и список из 1000 нарушений — допустимая ситуация. В SARIF есть явное предупреждение об усечении. В CLI список нарушений не ограничен этим серверным лимитом.

## 11. Самый простой первый запуск: только CLI

Этот маршрут позволяет понять проект без базы данных и сервера. Команды ниже написаны для **PowerShell на Windows**. Знак `PS>` из терминала вводить не нужно.

### Шаг 1. Откройте правильную папку

Если у вас уже есть рабочий каталог проекта, откройте PowerShell в нём. В Проводнике можно зайти в папку, нажать адресную строку, ввести `powershell` и нажать Enter.

Проверка:

```powershell
Get-Location
git branch --show-current
git status --short --branch
```

Ожидаемая ветка этого руководства — `codex/v1.1-fixes`. Если ветка другая или есть незнакомые незакоммиченные изменения, сначала выясните, кому они принадлежат. Не используйте сброс или принудительное переключение для «исправления» ситуации.

Если репозитория вообще нет, создайте отдельный клон:

```powershell
git clone --branch codex/v1.1-fixes https://github.com/IliyasNU/invariant.git invariant-learning
Set-Location .\invariant-learning
```

Для этого нужны установленные Git, Python 3.14 или новее и uv. Ссылки на официальную документацию приведены в конце. Если команда не найдена, это ещё не ошибка Invariant: терминал не видит соответствующую установленную программу.

### Шаг 2. Подготовьте окружение

```powershell
uv sync --locked --dev
uv run invariant --version
```

`uv sync` читает описания зависимостей, создаёт локальное окружение `.venv` и устанавливает пакеты. `--locked` проверяет соответствие `uv.lock`, а не незаметно обновляет версии. Окружение позволяет не смешивать библиотеки этого проекта с другими проектами компьютера.

Для описанного состояния ожидается версия `1.2.0`. Номер может измениться в следующих выпусках.

### Шаг 3. Проверьте готовый пример

```powershell
uv run invariant check examples/demo
```

Ожидается `PASS`: демонстрационный магазин соответствует своим четырём правилам. Это проверяет содержимое `examples/demo`, а не все папки компьютера.

Не нужно выполнять `invariant init` в корне самого Invariant: там конфигурация уже существует. Команда `init` нужна в **другом проверяемом проекте**, где конфигурацию только создают.

### Шаг 4. Получите машинный отчёт

```powershell
uv run invariant check examples/demo --format json
uv run invariant check examples/demo --format sarif
```

Первый вариант удобен для обычной обработки JSON. Второй создаёт документ стандарта SARIF. Оба здесь просто печатают текст в терминал.

Чтобы сохранить SARIF в UTF-8, в том числе в Windows PowerShell 5.1:

```powershell
$utf8 = New-Object System.Text.UTF8Encoding($false)
$oldConsoleEncoding = [Console]::OutputEncoding
try {
    [Console]::OutputEncoding = $utf8
    $report = uv run invariant check examples/demo --format sarif
    $exitCode = $LASTEXITCODE
    [System.IO.File]::WriteAllText((Join-Path (Get-Location).Path 'demo-results.sarif'), ($report -join "`n"), $utf8)
}
finally {
    [Console]::OutputEncoding = $oldConsoleEncoding
}
$exitCode
```

Здесь результат — текст, а не исполняемая программа. Временная настройка декодирования нужна, чтобы PowerShell 5.1 правильно прочитал UTF-8-вывод CLI с кириллицей; затем прежняя настройка возвращается. Перед перезаписью одноимённого отчёта сохраните нужную старую копию.

Коды завершения CLI:

| Код | Значение |
| --- | --- |
| `0` | `pass` либо `not_applicable` |
| `1` | Блокирующие нарушения |
| `2` | Неполная проверка, ошибка входа/конфигурации или техническая ошибка |

Чтобы отсутствие применившихся проверок тоже считалось ошибкой, добавьте `--strict`.

## 12. Свой проверяемый проект и Git-изменения

В каталоге собственного Python-проекта можно создать конфигурацию:

```powershell
invariant init
```

Эта команда доступна напрямую, если CLI установлен в активном окружении или доступен через PATH. Не переносите команду `uv run` в любой случайный каталог без понимания, какое uv-окружение там выбрано. Альтернатива — вызвать установленный `invariant.exe` по полному пути к нужной `.venv\Scripts`.

Сгенерированный файл — только отправная точка. Измените имена пакетов и правила под свой проект. Правило для `shop.domain.*` бессмысленно, если такого модуля в проекте нет: возможен `not_applicable`.

Для анализа закоммиченных изменений:

```powershell
invariant check . --base origin/main --head HEAD
```

Это имеет смысл в проверяемом Git-репозитории, где существует `origin/main`. Режим читает файлы из указанного head-коммита и сравнивает изменения относительно merge base с базовой ревизией. **Незакоммиченные изменения рабочего каталога в этот режим не входят.** Для них используйте обычный `invariant check .`.

Проверять другие языки эта версия не умеет. Наличие C++-эксперимента в репозитории не означает поддержку анализа `.cpp`.

## 13. Запуск полного сервиса через Docker Compose

Понадобится установленный и работающий Docker Desktop с Linux-контейнерами и Compose. Это уже маршрут для серверной части; CLI из предыдущего раздела от него не зависит.

### Подготовьте настройки, не стирая существующие

В корне правильного checkout:

```powershell
if (-not (Test-Path -LiteralPath .env)) {
    Copy-Item -LiteralPath .env.example -Destination .env
}
notepad .env
```

Если `.env` уже существует, он может содержать ваши пароли и ключи. Не заменяйте его шаблоном.

Рекомендуемый режим для знакомства с API — с ключом. Сгенерируйте случайное значение:

```powershell
uv run python -c "import secrets; print(secrets.token_urlsafe(32))"
```

Скопируйте результат в `.env` после `INVARIANT_API_KEY=`. Ключ должен быть не короче 32 символов. Не публикуйте его, не отправляйте в резюме и не добавляйте `.env` в Git.

Настройки `POSTGRES_*` из шаблона предназначены для локального знакомства. Они не являются готовой производственной конфигурацией.

Без API-ключа приложение не стартует, если явно не выбран `INVARIANT_LOCAL_ONLY=true`. Этот режим допускается только для сервиса, доступного с вашего компьютера. Он не заменяет проверку адреса прослушивания и сетевых настроек.

### Запустите компоненты

```powershell
docker compose up --build -d
docker compose ps -a
```

Что запускается:

| Сервис Compose | Назначение | Ожидаемое состояние |
| --- | --- | --- |
| `db` | PostgreSQL 18 | Работает, healthcheck проходит |
| `migrate` | Однократно применяет миграции | Успешно завершён: `Exited (0)` — нормально |
| `app` | HTTP API | Работает, readiness проходит |
| `worker` | GitHub-задачи | Работает, heartbeat обновляется |

Порядок: сначала готовится БД, затем выполняются миграции, потом стартуют API и worker. Все серверные процессы используют один образ приложения. Отдельного «контейнера C++» нет.

Проверка API:

```powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:8000/health'
Invoke-RestMethod -Uri 'http://127.0.0.1:8000/ready'
```

`/health` проверяет, что процесс отвечает. `/ready` дополнительно проверяет доступ к БД и актуальность схемы. «Процесс жив» и «сервис готов обслуживать запросы» — разные вещи.

Откройте в браузере `http://127.0.0.1:8000/docs`. Это интерактивная документация FastAPI, а не отдельный пользовательский frontend. Через `Authorize` можно указать API-ключ и попробовать операции.

### Порты и адреса

- API с вашего компьютера: `127.0.0.1:8000`.
- PostgreSQL с вашего компьютера: `127.0.0.1:5433`.
- PostgreSQL для контейнеров Compose: `db:5432`.

`127.0.0.1` означает «этот компьютер». Порт — номер сетевого входа конкретного процесса. `5433` на хосте выбран, чтобы не конфликтовать с PostgreSQL, который может уже занимать стандартный `5432`.

Если порт занят, сначала выясните кем. Не завершайте чужие процессы наугад. Для этой проверки можно использовать:

```powershell
Get-NetTCPConnection -LocalPort 8000 -State Listen -ErrorAction SilentlyContinue
Get-NetTCPConnection -LocalPort 5433 -State Listen -ErrorAction SilentlyContinue
docker compose ls
```

`APP_PORT` и `POSTGRES_PORT` можно переопределить для другого экземпляра. Но тогда изменятся и адреса в ваших командах.

## 14. Первая полезная работа с API: весь сценарий в PowerShell

Этот сценарий предполагает, что API из предыдущего раздела уже работает. Команды создадут отдельный учебный проект и один анализ. Они не изменяют правила других проектов.

### Авторизация

```powershell
$base = 'http://127.0.0.1:8000'
$apiKey = Read-Host 'Вставьте INVARIANT_API_KEY из настроек запущенного API'
$headers = @{ Authorization = "Bearer $apiKey" }
```

`.env` не создаёт автоматически переменные PowerShell. Если ключ указан в файле, это ещё не означает, что в текущем терминале существует `$env:INVARIANT_API_KEY`.

Для удобства добавим функцию отправки JSON. Она переводит русские строки в UTF-8 и подходит в том числе для Windows PowerShell 5.1:

```powershell
function Send-InvariantJson {
    param([string]$Path, [hashtable]$Payload, [string]$Method = 'Post')
    $json = $Payload | ConvertTo-Json -Depth 10
    $bytes = [System.Text.Encoding]::UTF8.GetBytes($json)
    Invoke-RestMethod -Method $Method -Uri "$base$Path" -Headers $headers -ContentType 'application/json; charset=utf-8' -Body $bytes
}
```

### Создайте проект

```powershell
$project = Send-InvariantJson -Path '/projects' -Payload @{
    name = "Учебный проект $(Get-Date -Format 'yyyyMMdd-HHmmss')"
    description = 'Знакомство с архитектурными правилами'
    source_roots = @('src')
}
$projectId = $project.id
$project
```

Проект — контейнер настроек и правил, а не автоматически склонированный репозиторий. Не предполагайте, что его ID будет равен 1: используйте значение из ответа.

### Создайте правило

```powershell
$rule = Send-InvariantJson -Path "/projects/$projectId/rules" -Payload @{
    key = 'domain-isolation'
    name = 'Домен не зависит от инфраструктуры'
    rule_type = 'forbidden_import'
    source_pattern = 'app.domain.*'
    forbidden_imports = @('app.infrastructure')
}
$rule
```

### Отправьте текст на проверку

```powershell
$run = Send-InvariantJson -Path "/projects/$projectId/analyze" -Payload @{
    files = @(
        @{
            path = 'src/app/domain/payment.py'
            content = "from app.infrastructure.db import engine`n"
        }
    )
}
$runId = $run.id
$run.outcome
$run.summary
$run.violations | Format-List
```

Ожидается `fail`: правило нашло запрещённый импорт. Наличие реального модуля `app.infrastructure.db` на вашем компьютере не требуется, потому что Invariant не выполняет этот код.

Ответ HTTP `200` здесь означает «сервер обработал запрос». Он не означает, что архитектурная проверка прошла. Всегда смотрите на `outcome`.

### Прочитайте историю и скачайте отчёт

```powershell
Invoke-RestMethod -Uri "$base/projects/$projectId/analysis-runs" -Headers $headers
Invoke-RestMethod -Uri "$base/analysis-runs/$runId" -Headers $headers
Invoke-RestMethod -Uri "$base/projects/$projectId/stats" -Headers $headers
$reportPath = Join-Path (Get-Location).Path "invariant-run-$runId.sarif"
Invoke-WebRequest -Uri "$base/analysis-runs/$runId/sarif" -Headers $headers -OutFile $reportPath -UseBasicParsing
$reportPath
```

SARIF не исправляет код и не отправляется автоматически в GitHub code scanning. Это файл отчёта, который может прочитать совместимый инструмент. Для публикации в другой системе нужна отдельная настройка.

Старый анализ не переписывается при изменении правил: экспорт использует сохранённый снимок. Для `queued`, `running`, `failed` SARIF возвращает `409 analysis_not_completed`. Для старых запусков без поддерживаемого снимка — `409 sarif_unavailable`; JSON-история при этом остаётся доступной.

## 15. Карта API и основные ошибки

`{id}` ниже — число, полученное от API; это не строка, которую следует вводить буквально с фигурными скобками.

| Операция | Адрес | Назначение |
| --- | --- | --- |
| POST / GET | `/projects` | Создать проект / получить список |
| GET / PATCH / DELETE | `/projects/{id}` | Получить / изменить / удалить проект |
| POST / GET | `/projects/{id}/rules` | Создать правило / получить правила |
| GET / PATCH / DELETE | `/projects/{id}/rules/{rule_id}` | Работа с одним правилом |
| GET | `/projects/{id}/config` | Конфигурация проекта как TOML |
| POST | `/projects/{id}/config/import` | Предпросмотр или применение конфигурации |
| POST | `/projects/{id}/analyze` | Проверить переданные тексты сразу |
| POST | `/projects/{id}/analyze/github` | Поставить PR в очередь, ответ `202` |
| GET | `/projects/{id}/analysis-runs` | История проекта |
| GET | `/projects/{id}/stats` | Статистика запусков |
| GET | `/analysis-runs/{id}` | Полный сохранённый запуск |
| GET | `/analysis-runs/{id}/diagnostics` | Диагностики с пагинацией и фильтрами |
| GET | `/analysis-runs/{id}/result` | JSON-экспорт |
| GET | `/analysis-runs/{id}/sarif` | SARIF-экспорт |
| POST | `/integrations/github/webhook` | Уведомления GitHub с HMAC-подписью |

Списки поддерживают пагинацию: `limit` задаёт размер страницы, `offset` — сколько записей пропустить. Заголовок `X-Total-Count` сообщает общее число совпадений до разбиения на страницы. У списка диагностик это число сохранённых строк, а не обязательно полное число всех найденных нарушений.

Правила фильтруются по `enabled`, `severity`, `rule_type`. История — по статусу, исходу, источнику и номеру PR. Статистика считает pass rate только среди запусков с вердиктом `pass`/`fail`; отсутствие вердикта показывается отдельно.

Полезные HTTP-коды:

| Код | Как понимать |
| --- | --- |
| `200` | Операция обработана; исход анализа нужно читать отдельно |
| `201` | Объект создан |
| `202` | Задача принята или событие корректно проигнорировано; это не готовый результат анализа |
| `401` | Нет подходящего API-ключа или неверна подпись webhook |
| `404` | Нужный проект, правило или запуск не найден |
| `409` | Конфликт: например, имя уже занято или SARIF пока недоступен |
| `413` | Тело запроса слишком велико |
| `422` | Не подходят поля запроса; это не то же самое, что синтаксическая ошибка внутри проверяемого Python-файла |
| `429` | Превышен установленный лимит запросов/анализов |
| `503` | Например, недоступна БД или webhook не настроен |

Ошибки имеют общий JSON-формат с `error.code`, `message` и `request_id`. Заголовок `X-Request-ID` помогает найти связанный запрос в логах.

`DELETE /projects/{id}` удаляет также его правила и историю. Не используйте удаление как способ «перезапустить приложение».

## 16. Что хранится в базе данных

Основные модели описаны в `app/models.py`:

```text
Project
├── Rule                       правила проекта
├── AnalysisRun                отдельные запуски
│   └── AnalysisViolation      нарушения и ошибки анализа
└── PullRequestComment         запись о комментарии к PR
```

`AnalysisRun` хранит не только «хорошо/плохо», но и источник, статус, итог, счётчики, время работы, версию движка, снимок конфигурации и её SHA-256. Для GitHub добавляются репозиторий, номер PR, идентификаторы коммитов и доставки.

`AnalysisViolation` сохраняет координаты, сообщение, тип диагностики, важность и данные правила. При удалении правила его связь может стать пустой, но записанное имя/ключ и само историческое нарушение остаются. Это позволяет читать старую историю без подмены её сегодняшними правилами.

`PullRequestComment` нужен, чтобы редактировать существующий комментарий, а не писать новый после каждого запуска.

Исходные тексты файлов сервис обрабатывает в памяти и не сохраняет как исходники в PostgreSQL. История всё равно содержит чувствительные для проекта метаданные: пути, имена модулей, правила и сообщения. Поэтому её тоже нельзя считать общедоступной по умолчанию.

Alembic применяет последовательность миграций. На описанном состоянии head — `20261024_0007`. Версия 1.2.0 использует эту же схему; отдельная миграция для SARIF не потребовалась.

Транзакция — группа изменений, которая фиксируется вместе. Например, результат запуска и связанные диагностики записываются согласованно. Ограничения БД дополнительно защищают уникальность имён и допустимые сочетания статусов/исходов.

## 17. Как работают GitHub, webhook и worker

### Ручная постановка PR в очередь

У проекта должны быть указаны `github_owner` и `github_repo`. Их можно добавить через `PATCH /projects/{id}`. Затем запросить анализ:

```json
{"pull_number": 12}
```

Такое тело отправляется в `POST /projects/{id}/analyze/github`. Число 12 — пример: нужен существующий номер PR именно в настроенном репозитории.

API возвращает `202` и сохранённый запуск со статусом `queued`. Запрос не ждёт скачивания всех файлов. Worker забирает задачу, обращается к GitHub, запускает общее ядро и сохраняет результат. Клиент может опрашивать `GET /analysis-runs/{id}` до `completed` или `failed`.

Для публичного репозитория часть операций чтения возможна без GitHub-токена, но с меньшими лимитами API. Приватные репозитории и публикация комментариев требуют подходящего доступа.

### Автоматический webhook

Webhook сообщает: «PR открыли, обновили или открыли снова». Invariant принимает действия `opened`, `synchronize`, `reopened`; остальные корректно игнорирует.

Для GitHub нужен доступный извне HTTPS-адрес. `http://127.0.0.1:8000` у вас на компьютере GitHub не видит. Публикация сервиса через HTTPS-прокси или туннель — отдельная эксплуатационная задача, не обязательная для первого локального знакомства.

Настройки webhook: тип содержимого `application/json`, события Pull requests, адрес `/integrations/github/webhook`, согласованный секрет.

### Три разных ключа

| Настройка | Кто использует | Для чего |
| --- | --- | --- |
| `INVARIANT_API_KEY` | Клиент Invariant | Доступ к бизнес-операциям API через Bearer-заголовок |
| `GITHUB_TOKEN` | Invariant как клиент GitHub | Чтение закрытых данных, более высокие лимиты, необязательные комментарии |
| `GITHUB_WEBHOOK_SECRET` | GitHub и принимающий API | Проверка HMAC-подписи пришедшего уведомления |

Это не ключи OpenAI. В работающем анализаторе нет обращения к LLM.

Подпись webhook вычисляется по точным байтам тела. Проверка использует HMAC-SHA256 и сравнение, предназначенное для защиты от утечки через время сравнения. API-ключ не заменяет webhook-секрет.

### Как защищена очередь

- `X-GitHub-Delivery` сохраняется с уникальным ограничением: повторная доставка возвращает существующий запуск.
- Worker захватывает задачу с помощью блокировки строки и lease — временного права её обрабатывать.
- У задачи есть ограничение попыток и отложенные повторы для временных сбоев.
- Если worker умер, lease истекает, и задачу можно восстановить.
- Worker, потерявший владение, не должен переписать результат нового владельца.

По умолчанию используются до трёх попыток, lease около 10 минут и рабочий лимит около 5 минут. Реальная длительность зависит от настроек; задержка повторов растёт и ограничена сверху. Большой некорректный `Retry-After` не превращается в бесконечное ожидание.

GitHub-файлы читаются для зафиксированного head-коммита. Если PR сдвинулся во время получения списка файлов, попытка повторяется вместо смешивания двух состояний кода.

Комментарии включаются только при наличии токена и `GITHUB_POST_PR_COMMENT=true`. Ошибка комментария не меняет результат анализа: обратная связь повторяется отдельно. Устаревшие результаты не должны выдавать старый PASS за текущий. Если проект перенастроили на другой репозиторий, уже поставленная задача сохраняет исходный репозиторий, а её обратная связь может стать `stale`.

## 18. Безопасная повседневная работа и диагностика

### Логи и остановка

```powershell
docker compose logs --tail 100 app worker db
docker compose stop
```

Смотрите на код ошибки и request ID. Не публикуйте весь лог без просмотра: в нём могут быть пути и служебные данные. Секреты редактируются логирующей системой, но это не повод обращаться с логами как с публичными данными.

`docker compose down` удаляет контейнеры/сеть этого Compose-проекта, сохраняя именованный том БД. Не добавляйте `-v`, если хотите сохранить данные. `alembic downgrade base` — не обычная команда запуска: она откатывает схему и может уничтожить данные.

При нескольких копиях репозитория Compose может выбрать разные имена проектов и тома. Пустая история после запуска из другой папки не обязательно означает потерю старой БД. Сначала проверьте `docker compose ls`, а не удаляйте тома.

Изменение `POSTGRES_PASSWORD` в `.env` не меняет автоматически пароль уже инициализированной базы в существующем томе.

### Предпросмотр импорта конфигурации

У импорта `dry_run` по умолчанию выключен. Если хотите только увидеть изменения, это нужно указать явно:

```powershell
$toml = Get-Content -LiteralPath '.\examples\demo\invariant.toml' -Raw -Encoding UTF8
$plan = Send-InvariantJson -Path "/projects/$projectId/config/import" -Payload @{
    content = $toml
    mode = 'merge'
    dry_run = $true
}
$plan
```

Команда использует функцию и переменные из раздела 14. `merge` сохраняет правила, которых нет в файле. `replace` удаляет отсутствующие правила: не применяйте этот режим без проверки плана.

### Резервная копия в PowerShell

Сначала проверьте имя своей БД и пользователя; ниже стандартные локальные значения шаблона. Команды записывают dump в контейнере и затем копируют бинарный файл наружу:

```powershell
New-Item -ItemType Directory -Path '.\backups' -Force | Out-Null
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
$containerBackup = "/tmp/invariant-$stamp.dump"
docker compose exec -T db pg_dump -U invariant -d invariant -Fc -f $containerBackup
if ($LASTEXITCODE -ne 0) { throw 'Резервная копия не создана' }
docker compose cp "db:$containerBackup" ".\backups\invariant-$stamp.dump"
```

Не переносите слепо Bash-пример с бинарным перенаправлением `>` в Windows PowerShell 5.1: он может изменить байты. Восстановление лучше сначала проверить в отдельной пустой базе. Файл dump может содержать приватную историю проекта; не добавляйте его в публичный Git-репозиторий.

### Очистка старой истории

Сначала можно только посчитать кандидатов на удаление:

```powershell
docker compose exec worker python -m app.retention --days 90 --dry-run
```

Без `--dry-run` эта команда уже удаляет подходящие завершённые запуски. По умолчанию история хранится без ограничения срока.

Техническая оговорка версии 1.2.0: переменная `INVARIANT_RETENTION_DAYS` поддерживается worker-настройками, но в текущем `compose.yaml` не проброшена в окружение контейнера. Одного добавления строки в `.env` недостаточно, чтобы включить автоматическую очистку Docker-worker. Ручной предпросмотр выше работает отдельно; для автоматизации потребуется явно настроить передачу переменной.

### Если что-то не работает

| Симптом | Что проверить первым |
| --- | --- |
| Команда `uv` / `git` / `docker` не найдена | Установлена ли программа и доступна ли в PATH; после установки может понадобиться новый терминал |
| Неверная версия Python | Требуется 3.14+, не 3.13 |
| API не стартует без ключа | Заполнен ли `INVARIANT_API_KEY` или осознанно выбран локальный режим |
| `401` | Совпадает ли Bearer-ключ с настройками запущенного сервиса |
| `/health` работает, `/ready` нет | Доступна ли БД, выполнены ли миграции |
| Ошибка занятого порта | Не работает ли уже API/БД или другой Compose-проект |
| `queued` не меняется | Запущен ли worker; не назначена ли следующая попытка на будущее |
| Не находится ни одного нарушения | Совпадают ли реальные имена модулей с `source_pattern` и правильно ли выбраны `source_roots` |
| `incomplete` | Посмотрите `analysis_errors`: возможно, файл не разбирается или превышен лимит |
| Нет комментария в PR | Токен, права, флаг комментариев и состояние `feedback` |
| Неверная подпись webhook | Один ли секрет у GitHub и приложения; приложение надо перезапустить после изменения настроек |
| Docker Desktop не запускает engine | Это проблема окружения Docker; не делайте factory reset и не удаляйте тома как первый шаг |

## 20. Тесты, CI и фактические результаты проверки

Для локальной безопасной проверки используется SQLite в памяти:

## 21. Производительность и почему C++ пока не подключён

C++ рассматривался как возможный ускоритель, а не как новый язык всего проекта. Измерения сначала показали повторную работу Python: многократные обходы AST и создание диагностик, которые затем выбрасывались из-за лимита.

После оптимизации Python в пяти опубликованных сценариях медианное время уменьшилось примерно в **1,7–14,7 раза** по сравнению с 1.1.0. Проверялись совпадение итогов и отпечатков диагностик: более быстрый, но другой результат не должен считаться улучшением.

Эти числа относятся к конкретным синтетическим сценариям на одной Windows-машине. Они не обещают ускорение любого проекта в 15 раз, не показывают запросы в секунду всего сервиса и не доказывают снижение пиковой памяти. Измеренный `tracemalloc`-пик остался примерно тем же, местами немного вырос. `tracemalloc` учитывает не всю память процесса.

В отдельной C++-пробе само вычислительное ядро проверки префиксов было быстрее аналогичного Python-алгоритма, но полный вариант с отдельным процессом и передачей данных оказался медленнее Python. Нативное расширение внутри 64-битного Python не было измерено: имевшийся компилятор собирал 32-битный код.

Поэтому рабочий движок остаётся Python. C++-проба лежит в `benchmarks/`, не загружается приложением и не нужна для установки.

Важный инженерный вывод: сначала измерить узкое место и убрать лишнюю работу, а уже затем рассматривать стоимость дополнительного языка, сборки, платформенных wheel и поддержки.

Источник измерений: [performance.md](https://github.com/IliyasNU/invariant/blob/codex/v1.1-fixes/docs/performance.md).

## 22. Ограничения: что нельзя обещать пользователю и работодателю

У текущего проекта нет:

- ИИ-модели, автоматически понимающей или проектирующей архитектуру;
- полноценного анализа типов и всех потоков данных;
- гарантии обнаружения каждого запрещённого вызова;
- поддержки анализа C++, JavaScript и других языков;
- полноценного графа всех зависимостей репозитория;
- отдельного frontend, пользовательских кабинетов и ролей;
- GitHub App-авторизации и GitHub Check Runs;
- доказанной промышленной эксплуатации с заявленным SLA.

Динамические импорты и вызовы через переданные функции, `getattr` или промежуточные переменные не восстанавливаются как полное поведение программы. Например, `runner = os.system; runner(...)` не стоит считать гарантированно распознаваемым случаем.

CLI проверяет выбранное дерево, а GitHub-интеграция — изменённые файлы PR, не весь неизменившийся репозиторий. Для CLI/GitHub предусмотрены ограничения чтения UTF-8 Python-файлов до 1 000 000 байт; в GitHub есть и общие лимиты ответа, объёма и времени. Пропущенная проверка должна быть видна в результате.

Один API-ключ даёт доступ ко всем бизнес-операциям. Это не многопользовательская система разграничения прав. CORS тоже не является заменой авторизации или HTTPS.

Эти ограничения не обесценивают проект. Они показывают границы инструмента. Хорошая инженерная документация объясняет не только успешные случаи, но и то, чего программа не знает.

## 23. Как показать проект работодателю и подготовиться к разговору

### Короткая презентация

Можно сказать:

> «Invariant — инструмент контроля архитектурных правил Python-проектов. В нём общее AST-ядро для CLI, API и GitHub PR. Есть четыре типа правил, PostgreSQL-история, очередь с worker, подписанные webhook и SARIF-экспорт. Проект демонстрирует backend-разработку, работу с БД, интеграции, тестирование и профилирование. Я могу показать конкретное правило, нарушение и путь запроса по коду».

Эту формулировку следует использовать как описание проекта. Утверждения «я самостоятельно реализовал каждую часть» требуют реального подтверждения вашим участием и пониманием.

### Демонстрация по шагам

1. Показать дерево `examples/demo` и одно понятное правило.
2. Запустить CLI на чистом примере: увидеть `PASS`.
3. На отдельной учебной копии добавить запрещённый импорт и увидеть конкретную строку нарушения.
4. Показать тот же смысл через API из раздела 14.
5. Открыть историю и SARIF; объяснить, почему старый отчёт не меняется после удаления правила.
6. Открыть соответствующий тест и объяснить, какую ошибку он предотвращает.
7. При вопросе о скорости показать измерения и честно объяснить решение по C++.

Не изменяйте основной demo перед собеседованием без отдельной копии или ясного плана возврата изменений. Нельзя выдавать специально подготовленный успешный пример за доказательство всех возможных сценариев.

### Вопросы, к которым стоит подготовиться

**Почему FastAPI?** Для явного HTTP API, валидации и OpenAPI. Сам движок от FastAPI не зависит.

**Почему PostgreSQL, а не просто файл?** Сервису нужны связанные данные, история, уникальность и транзакции. Очередь также использует блокировки БД. В CLI хранилище не нужно.

**Почему нет Redis/Celery?** Очередь текущего масштаба реализована через таблицу запусков. Это уменьшает количество инфраструктуры. Это выбор для имеющихся требований, а не доказательство, что такая схема подходит любой нагрузке.

**Зачем отдельный worker?** Скачивание PR и анализ не должны удерживать HTTP-запрос до конца. Задача сначала надёжно записывается, затем обрабатывается отдельно.

**Как избежать дублей webhook?** Уникальный delivery ID в БД и возврат уже созданного запуска.

**Как отличить нарушение от ошибки инструмента?** По `kind`, `status`, `outcome` и отдельным счётчикам. Отсутствие применимых правил не объявляется успешной проверкой.

**Зачем снимок правил?** Чтобы исторический отчёт описывал старую проверку, а не сегодняшнюю конфигурацию.

**Почему AST вместо поиска строк?** AST отличает настоящие конструкции языка от комментариев и строк и даёт структурную информацию. Но AST сам по себе не даёт полного понимания выполнения программы.

**Что улучшать дальше?** Реальные профили больших репозиториев, эксплуатационную проверку Docker/CI, более удобный onboarding, GitHub App/Checks, дополнительные детерминированные правила. Каждое улучшение нужно выбирать под конкретную задачу.

### Если часть работы сделана с ИИ

В истории проекта есть вклад AI-инструментов. Не нужно его скрывать или превращать репозиторий в заявление о навыках, которых пока нет. На интервью лучше честно разделить: что вы придумали, что реализовали с помощью ИИ, что проверили и что уже способны объяснить самостоятельно.

Практический ориентир: уметь проследить один запрос от JSON до ответа, объяснить одну модель БД, одно правило и один тест. Работодатель может проверить именно это, а не количество терминов в описании.

## 24. План изучения проекта с нуля

Не пытайтесь освоить весь стек сразу. Двигайтесь по небольшим проверяемым шагам:

1. **Python-основа:** переменная, список, словарь, функция, `import`, исключение. Прочитать простое правило и предсказать его результат.
2. **Файлы и терминал:** понять текущую папку, относительный путь, команду и код завершения.
3. **CLI:** выполнить раздел 11 и объяснить различие `pass`, `fail`, `incomplete`.
4. **JSON и HTTP:** создать учебный проект через API; найти его ID в ответе.
5. **Pydantic:** посмотреть, почему пустое имя или неправильный тип отвергаются.
6. **БД:** найти в моделях связи проекта, правила и запуска. Понять отличие записи от таблицы и транзакции от одного запроса.
7. **Ядро:** найти AST-узел импорта и функцию, создающую диагностику.
8. **Тесты:** выбрать существующий тест, поменять только учебный вход и заранее предположить результат.
9. **GitHub-очередь:** нарисовать путь `queued → running → completed/failed` и объяснить повторные попытки.
10. **Собственная небольшая доработка:** добавить проверяемое улучшение документации или тестового случая, не меняя десять компонентов одновременно.

Вы будете понимать проект лучше, когда сможете отвечать на конкретные вопросы «какие данные входят?», «какая функция их обрабатывает?», «что сохраняется?» и «как проверить результат?». Знать названия всех библиотек для этого недостаточно.

Для сохранения собственных изменений сначала смотрите diff и добавляйте конкретные файлы:

```powershell
git status --short --branch
git diff
git add docs/guide-ru.md
git commit -m "docs: clarify beginner guide"
```

Последние две команды уместны только после ваших реальных изменений этого файла. Не коммитьте `.env`, дампы базы, токены и личные отчёты. Не используйте `git reset --hard`, принудительный push или merge в `main` просто для «наведения порядка».

Локальный commit сохраняет историю на вашем компьютере. Push публикует её в удалённом репозитории. Merge объединяет ветки — это третья, отдельная операция. Сохранить работу на GitHub не означает автоматически объединить её с `main`.

Это руководство описывает конкретную версию проекта. Если код изменился, сверяйте примеры с `pyproject.toml`, OpenAPI и актуальным отчётом проверки, а не считайте старый текст гарантией будущего поведения.
